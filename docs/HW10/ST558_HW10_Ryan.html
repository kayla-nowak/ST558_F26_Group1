6. Summary Statistics

To avoid repeating the same summarize() code for each grouping, we write a helper that summarizes bike count by whatever grouping variables we pass it.

bike_summary <- function(data, ...) {
  data |>
    group_by(...) |>
    summarize(
      n      = n(),
      total  = sum(bike_count),
      mean   = mean(bike_count),
      sd     = sd(bike_count),
      min    = min(bike_count),
      median = median(bike_count),
      max    = max(bike_count),
      .groups = "drop"
    )
}

Cross-Validation Folds

Each fold holds out about 26 days. That’s small enough that some rare season and holiday combinations may be missing from a fold’s analysis set, which matters once we add the season by holiday interaction.

Fitting MLR Models

Recipe 1: Main Effects

We build the recipe on the training data. bike_count ~ . makes every other column a predictor. Then we change date to an ID role, so it stays in the data but isn’t used as a predictor.

recipe_1 <- recipe(bike_count ~ ., data = bike_train) |>
  update_role(date, new_role = "ID") |>
  step_date(date, features = "dow") |>
  step_mutate(
    day_type = factor(
      if_else(date_dow %in% c("Sat", "Sun"), "Weekend", "Weekday"),
      levels = c("Weekday", "Weekend")
    )
  ) |>
  step_rm(date_dow) |>
  step_relevel(holiday, ref_level = "No Holiday") |>
  step_normalize(all_numeric_predictors()) |>
  step_dummy(seasons, holiday, day_type)

Recipe 2: Adding Interactions

step_interact() has to come after step_dummy(), because it multiplies columns that already exist. By that point seasons has become three dummy columns (seasons_Spring, seasons_Summer, seasons_Winter), so we use starts_with("seasons_") to interact all three at once. The interactions also come after step_normalize(), so they’re products of the standardized variables.

recipe_2 <- recipe_1 |>
  step_interact(
    terms = ~ starts_with("seasons_"):holiday_Holiday +
      starts_with("seasons_"):temp +
      temp:rainfall

Because we set importance = "impurity" in the engine, ranger stores the importance values in variable.importance. enframe() turns that named vector into a tibble we can plot.

rf_final |>
  extract_fit_engine() |>
  pluck("variable.importance") |>
  enframe(name = "term", value = "importance") |>
  mutate(term = fct_reorder(term, importance)) |>
  ggplot(aes(importance, term)) +
  geom_col(fill = "darkgreen") +
  labs(title = "Random Forest Variable Importance", x = "Importance", y = NULL)

Temperature is the most important predictor in both plots, but the rest of the order differs. ranger only credits the variable a split actually used. rpart, whose importance baguette uses, also gives partial credit to surrogate splits, so dew point temperature (correlated 0.96 with temperature) ranks much higher in the bagged tree plot.
